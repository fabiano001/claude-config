# Validate Intake

## Model Recommendation

> **Use a sonnet-tier model** (Claude `claude-sonnet-4-6` or OpenAI `o3-mini`).
>
> Intake validation is deterministic — the TypeScript validator handles all
> checks. The agent's role is to present results clearly and suggest fixes.

This command validates an **intake YAML template** before executing a workflow.
Intake templates are the input forms that drive `/mobius:add-service`,
`/mobius:migrate-ecs-service`, `/mobius:new-hub`, and `/mobius:new-spoke`.

It catches:
- Missing required fields for the workflow type
- Invalid field values (bad environment names, malformed repo URLs)
- Inconsistent field combinations (e.g., gateway enabled but no hostnames)
- Schema violations against the intake type's Zod schema
- Migration-parity gaps between source ECS and target EKS config

---

## Supported Intake Types

| Type | Used By | What It Validates |
|------|---------|-------------------|
| `add-service` | `/mobius:add-service` | Service name, repo, chart, environments, gateway, IRSA |
| `migration` | `/mobius:migrate-ecs-service` | ECS source config, EKS target config, mapping rules |
| `migration-parity` | `/mobius:migrate-ecs-service` | Feature parity between ECS source and generated EKS config |
| `new-hub` | `/mobius:new-hub` | Hub cluster name, VPC, region, addons, monitoring |
| `new-spoke` | `/mobius:new-spoke` | Spoke cluster name, hub reference, environments, addons |

## CLI Flags

| Flag | Description | Default |
|------|-------------|---------|
| `<type>` | Intake type (required): add-service, migration, migration-parity, new-hub, new-spoke | — |
| `<intake.yaml>` | Path to the intake YAML file (required) | — |
| `--output FORMAT` | Output format: `text` or `json` | text |
| `--appset PATH` | ApplicationSet YAML for cross-check (add-service only) | — |
| `--allow-blockers` | Allow migration to proceed even if blockers exist (migration only) | off |
| `--overlay-dir PATH` | Path to generated overlay directory (migration-parity only, required) | — |
| `--listener-rules-file PATH` | Listener rules YAML file (migration-parity only) | — |
| `--argocd-path PATH` | Path to iac-eks-argocd repo (new-hub, new-spoke only) | `../iac-eks-argocd` |

## Execution Flow

### Step 1: Identify the intake file

If the user provides a path, use it directly. If not, ask:

```
Which intake file would you like to validate?
```

Common locations:
- `/tmp/<service>-intake.yaml` (generated by add-service research phase)
- `docs/workflows/services/add-service-intake.yaml` (template)
- `docs/workflows/migration/migrate-ecs-intake.yaml` (template)

### Step 2: Run the validator

```bash
npx mobius-validate-intake <type> <path-to-intake.yaml> [--output json]
```

For migration-parity checks:
```bash
npx mobius-validate-intake migration-parity <intake.yaml> \
  --overlay-dir <path-to-overlay-dir> \
  [--listener-rules-file <path-to-listener-rules.yaml>]
```

### Step 3: Interpret results

If the validator reports failures, provide:
- **What failed**: The specific field or check that failed
- **Why it matters**: What would go wrong if the workflow ran with this intake
- **How to fix**: The exact YAML edit to resolve the issue

### Step 4: Suggest re-validation

After the user fixes issues:

```
Run again to verify:
  npx mobius-validate-intake <type> <path>
```

## Examples

### Validate a new service intake

```
/mobius:validate-intake add-service /tmp/my-api-intake.yaml
```

### Validate a migration intake

```
/mobius:validate-intake migration /tmp/migrate-payments-intake.yaml
```

### Check migration parity

```
/mobius:validate-intake migration-parity /tmp/<service>-intake.yaml \
  --overlay-dir ../helm-charts/argocd/<service>
```

### Validate a new hub intake

```
/mobius:validate-intake new-hub /tmp/new-hub-intake.yaml
```

### CI/CD integration (JSON output)

```
/mobius:validate-intake add-service /tmp/intake.yaml --output json
```
