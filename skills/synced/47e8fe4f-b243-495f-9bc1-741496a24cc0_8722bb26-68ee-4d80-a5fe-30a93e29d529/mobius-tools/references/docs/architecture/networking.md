# Networking Architecture

> How external traffic reaches services running in Mobius EKS clusters —
> DNS, load balancing, TLS, and routing.

---

## Overview

Traffic flows through five layers to reach a service:

```
Client (browser / API consumer)
    │
    ▼
Route53 (DNS resolution)
    │  resolves hostname to NLB IP
    ▼
Network Load Balancer (NLB)
    │  TLS termination (ACM certificate)
    ▼
Envoy Gateway (ingress controller)
    │  HTTP routing via HTTPRoute resources
    ▼
Kubernetes Service
    │  kube-proxy / eBPF (cilium)
    ▼
Pod (application container)
```

Each layer is managed by a different component, most of which are provisioned
via Crossplane claims or ArgoCD-managed addons.

## DNS: Route53

### Zone Structure

DNS zones are delegated across AWS accounts using `terraform-module-delegated-zone`:

```
Parent zone (operations account):
  bgrp.io
    │
    ├── ops.bgrp.io          → operations account
    │   ├── qa.ops.bgrp.io   → ops-qa cluster
    │   └── prod.ops.bgrp.io → ops-prod cluster
    │
    └── svc.bgrp.io          → service account
        ├── qa.svc.bgrp.io   → bg-qa cluster
        └── prod.svc.bgrp.io → bg-prod cluster
```

Each cluster has its own DNS zone. The delegation is created by Terraform
during cluster bootstrapping (`iac-terragrunt-core-infra`).

### Automatic DNS Records: external-dns

The `external-dns` controller watches HTTPRoute and Ingress resources. When
a new route is created with a hostname, external-dns automatically creates
the corresponding Route53 record pointing to the NLB.

```
HTTPRoute created with hostname: api.qa.svc.bgrp.io
  → external-dns detects the new hostname
  → Creates Route53 ALIAS record: api.qa.svc.bgrp.io → NLB DNS name
  → DNS propagates (TTL dependent)
```

Engineers do not create DNS records manually. The hostname in the HTTPRoute
or Ingress resource drives everything.

## Load Balancing: NLB

Each cluster has a Network Load Balancer (NLB) provisioned by the
`XGatewayNLBListener` Crossplane claim.

### NLB Listener Claim

```yaml
apiVersion: aws.platform.boatsgroup.com/v1alpha1
kind: XGatewayNLBListener
metadata:
  name: main-gateway-https
spec:
  clusterName: bg-qa
  listenerPort: 443
  protocol: TLS
  certificateArn: arn:aws:acm:<region>:<account>:certificate/<id>
  targetGroupPort: 8443
```

This creates:
- NLB listener on port 443 with TLS termination
- Target group pointing to Envoy Gateway pods
- ACM certificate attached for TLS

### TLS Termination

TLS terminates at the NLB using ACM certificates. Traffic between the NLB
and Envoy Gateway can be re-encrypted (TLS passthrough) or plain HTTP
depending on the listener configuration.

## ACM Certificates

ACM certificates are provisioned via the `XIngressACMCertificate` Crossplane
claim:

```yaml
apiVersion: aws.platform.boatsgroup.com/v1alpha1
kind: XIngressACMCertificate
metadata:
  name: qa-svc-wildcard
spec:
  domainName: "*.qa.svc.bgrp.io"
  validationMethod: DNS
  route53ZoneId: <zone-id>
```

DNS validation is automatic — the claim creates the required Route53 validation
records. Certificates renew automatically before expiration.

For internal services, cert-manager can issue certificates from a ClusterIssuer
instead of ACM:

```
Certificate → CertificateRequest → Order → Challenge → Issued
```

## Ingress: Envoy Gateway

Envoy Gateway is the ingress controller for all HTTP traffic. It replaces
traditional Nginx Ingress with Gateway API resources.

### Gateway Resource

Each cluster has a main Gateway:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: main-gateway
  namespace: envoy-gateway-system
spec:
  gatewayClassName: envoy
  listeners:
    - name: https
      protocol: HTTPS
      port: 8443
```

### HTTPRoute Resources

Services define routing rules via HTTPRoute:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api-node-payments
  namespace: api-node
spec:
  parentRefs:
    - name: main-gateway
      namespace: envoy-gateway-system
  hostnames:
    - "api-payments.qa.svc.bgrp.io"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: api-node-payments
          port: 3000
```

HTTPRoutes are typically generated by Helm charts via `gateway.enabled: true`
in the service's `values.yaml`. Engineers configure hostnames and paths in the
overlay values.

## Complete Traffic Flow Example

For a request to `api-payments.qa.svc.bgrp.io`:

```
1. DNS Lookup
   Client → Route53 → resolves to NLB IP (via ALIAS record)
   (Record created by external-dns watching HTTPRoute)

2. TLS Termination
   Client → NLB:443 → TLS terminated with ACM wildcard cert
   (Certificate provisioned by XIngressACMCertificate claim)

3. Load Balancing
   NLB → Target Group → Envoy Gateway pod (port 8443)
   (Target group created by XGatewayNLBListener claim)

4. HTTP Routing
   Envoy Gateway inspects Host header: api-payments.qa.svc.bgrp.io
   Matches HTTPRoute → forwards to Service: api-node-payments:3000

5. Service Routing
   Kubernetes Service → Pod endpoint (via Cilium eBPF or kube-proxy)

6. Application
   Pod receives the request and processes it
```

## Multi-Cluster Networking

In the hub-spoke model, each spoke cluster has its own:
- DNS zone (e.g., `qa.svc.bgrp.io`)
- NLB (via XGatewayNLBListener)
- Envoy Gateway installation
- ACM certificates (via XIngressACMCertificate)

There is no cross-cluster service mesh or shared ingress. Each cluster is
independently accessible via its own DNS zone.

Hub clusters (ops-*) have their own zone (e.g., `qa.ops.bgrp.io`) primarily
for ArgoCD UI and internal tooling endpoints.

## Debugging Network Issues

### Service Not Reachable

```bash
# 1. Check DNS resolution
dig api-payments.qa.svc.bgrp.io

# 2. Check if external-dns created the record
kubectl logs -n external-dns -l app.kubernetes.io/name=external-dns --tail=100 | grep "api-payments"

# 3. Check HTTPRoute status
kubectl get httproute -n <namespace> -o wide
kubectl describe httproute -n <namespace> <route-name>

# 4. Check Envoy Gateway is running
kubectl get pods -n envoy-gateway-system

# 5. Check NLB target health
aws elbv2 describe-target-health --target-group-arn <arn>
```

### Common Issues

| Symptom | Cause | Fix |
|---------|-------|-----|
| DNS not resolving | external-dns hasn't created record | Check external-dns logs; verify HTTPRoute hostname |
| 502 Bad Gateway | Envoy Gateway can't reach backend pods | Check pod health; verify Service selector matches |
| 503 Service Unavailable | No healthy targets in NLB target group | Check target group health; verify pod readiness |
| TLS certificate error | Wrong or expired certificate | Check ACM certificate; verify `certificateArn` in NLB claim |
| Connection timeout | Security group blocking traffic | Check NLB security groups; verify Envoy port matches |
| 404 Not Found | HTTPRoute hostname or path doesn't match | Verify hostname in values.yaml; check HTTPRoute rules |

### Where to Fix

| Component | Fix Repo | Fix Path |
|-----------|----------|----------|
| DNS records | Automatic (external-dns) | Fix HTTPRoute hostname in service values.yaml |
| NLB configuration | Service repo | XGatewayNLBListener claim in overlays |
| ACM certificates | Service repo | XIngressACMCertificate claim in overlays |
| HTTPRoute rules | Service repo | Gateway config in overlay values.yaml |
| Envoy Gateway itself | iac-eks-addons | envoy-gateway overlay |
| DNS zone delegation | iac-terragrunt-core-infra | Terragrunt delegated-zone module |
