## 2. Traffic Migration

> **WARNING**: These steps affect live traffic. Execute during a maintenance window
> or with appropriate change management approval.

### Option A: DNS-Based Cutover (Recommended for most services)

1. [ ] Record current DNS configuration
   ```bash
   dig {{SERVICE_HOSTNAME}} +short
   # Record: {{CURRENT_DNS_TARGET}}
   ```

2. [ ] Update DNS to point to EKS Gateway
   - Target: EKS Envoy Gateway NLB
   - TTL: Reduce to 60s before cutover, restore after validation
   - Method: Route53 console or IaC (preferred)

3. [ ] Verify traffic flowing to EKS
   ```bash
   kubectl logs -n {{EKS_NAMESPACE}} -l app.kubernetes.io/name={{SERVICE_NAME}} --tail=10 -f
   ```

4. [ ] Monitor error rates for 15 minutes
   - Check application logs for errors
   - Check HTTP 5xx rate
   - Check response latency

### Option B: Weighted Cutover (For high-traffic services)

1. [ ] Create Route53 weighted routing policy
   - ECS weight: 90, EKS weight: 10
2. [ ] Monitor both targets for 30 minutes
3. [ ] Shift to 50/50
4. [ ] Monitor for 30 minutes
5. [ ] Shift to 0/100 (EKS only)
6. [ ] Monitor for 30 minutes

- [ ] Service stable for {{SOAK_PERIOD}} (recommended: 24 hours for production, 4 hours for QA)
- [ ] No elevated error rates
- [ ] No elevated latency

## 4. Rollback Procedure

> Execute if validation fails or unexpected issues arise during cutover.

### Immediate Rollback (< 5 minutes)

1. [ ] Revert DNS to original ECS target
   ```bash
   # Original target: {{ORIGINAL_DNS_TARGET}}
   ```
2. [ ] Verify traffic returning to ECS
3. [ ] Confirm ECS service still running at desired count
   ```bash
   aws ecs describe-services \
     --cluster {{ECS_CLUSTER}} \
     --services {{ECS_SERVICE_NAME}} \
     --profile {{AWS_PROFILE}} \
     --query 'services[0].{desired:desiredCount,running:runningCount}' \
     --output table
   ```

### Post-Rollback Analysis

- [ ] Capture EKS pod logs for failure analysis
  ```bash
  kubectl logs -n {{EKS_NAMESPACE}} -l app.kubernetes.io/name={{SERVICE_NAME}} --all-containers --tail=100 > /tmp/{{SERVICE_NAME}}-rollback-logs.txt
  ```
- [ ] Document root cause
- [ ] Create follow-up ticket for resolution
- [ ] Re-attempt migration after fix

### Rollback Decision Matrix

| Symptom | Severity | Action |
|---------|----------|--------|
| 5xx errors > 1% | High | Immediate rollback |
| Latency > 3x baseline | High | Immediate rollback |
| Pods crashlooping | High | Immediate rollback |
| IRSA auth failures | High | Immediate rollback |
| Minor config differences | Low | Investigate, no rollback |
| Non-critical feature gap | Low | Document, no rollback |

## 5. Cleanup (After Successful Cutover)

> Only execute after the soak period completes successfully.

### ECS Decommission

- [ ] Scale ECS service to 0
  ```bash
  aws ecs update-service \
    --cluster {{ECS_CLUSTER}} \
    --service {{ECS_SERVICE_NAME}} \
    --desired-count 0 \
    --profile {{AWS_PROFILE}} \
    --region us-east-1
  ```
- [ ] Wait 7 days (grace period for rollback)
- [ ] Delete ECS service
- [ ] Remove ECS task definition (deregister)
- [ ] Remove ECS IAM task role (after confirming no other services use it)
- [ ] Remove ALB target group (if dedicated to this service)

### Documentation

- [ ] Notify dependent teams of new endpoint
- [ ] Close migration ticket
